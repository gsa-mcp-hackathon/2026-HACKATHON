## 3. Tool contract: `generate_diagram`

Inputs (exactly one of `data`, `fileBase64`, `workspacePath` is required):

| Param | Type | Notes |
|---|---|---|
| `data` | string | Raw text: JSON, CSV, YAML, Markdown, plain text |
| `fileBase64` | string | Base64 file bytes. Replaces the guide's `pdfBase64` so DOCX/XLSX/HTML work too |
| `fileName` | string | Required with `fileBase64`; extension drives the extractor (e.g. `plan.pdf`, `roster.xlsx`) |
| `workspacePath` | string | Must be under the caller's own `/Workspace/Users/<email>/` (or `/Users/<email>/`) |
| `diagramType` | string, optional | If it resolves via `findDiagramCatalogEntry`, skip Step 1 entirely (saves one LLM call) |
| `hint` | string, optional | One-line focus instruction passed to both steps |

Decision Q1: no `pdfBase64` alias. `fileBase64` + `fileName` is the only file-bytes input.

Size limits: `express.json({ limit: '20mb' })` for `/mcp`; reject decoded files over ~14 MB with `INVALID_INPUT`. Extracted text is truncated at 60,000 chars by the original extractor (it appends `[... truncated ...]`); report `truncated: true` in the response metadata.

Output on success:
1. `ImageContent` (`image/png`, base64 without data-URL prefix)
2. `TextContent` JSON: `{ status: "OK", diagramType, rationale, mermaidSource, endpointUsed, repaired, truncated, timingsMs }`

## 4. Pipeline and time budget

One request-wide deadline: `deadlineAt = start + 70_000` (5 s safety margin under the guide's 75 s proxy ceiling).

| Stage | Cap | Notes |
|---|---|---|
| Extract input | ≤ 10 s | Workspace export + parse. Abort with `EXTRACTION_FAILED` on overrun |
| Step 1: choose type | ≤ 12 s, `max_tokens` 512 | Skipped if `diagramType` resolves. Prompt = PROMPT 1 table rows for supported types only + JSON-only answer `{diagramType, rationale}`. Unresolvable answer → Flowchart |
| Step 2: write Mermaid | min(45 s, remaining − 25 s) | `buildDiagramSyntaxPrompt(name)` (sync; throws on unknown type) + "output one fenced mermaid block" |
| Render attempt 1 | min(remaining, 40 s) | `renderMermaid` has its own 20 s SVG + 20 s PNG timeouts and retries PNG twice; wrap the whole call in the remaining-time race and keep `.catch(() => {})` on the losing promise |
| Repair (only on `ValidationError`) | only if ≥ 20 s remain | One LLM call with the error text (truncated to ~500 chars), then one more render |

LLM call details (reuse the original's `invoke` approach):
* `POST {host}/serving-endpoints/{name}/invocations` with `{ messages, max_tokens }` (no `temperature`: `databricks-gemini-3-8-flash` rejects it with HTTP 400, found in the first Phase 1 startup trace), bearer = app service-principal token from `getAccessToken()`.
* Endpoints: `LLM_ENDPOINT_PRIMARY` → `LLM_ENDPOINT_FALLBACK`, for both Step 1 and Step 2. Since D27 (2026-11-05): Claude Haiku 4.5 → GPT-5.4 Mini (originally Q5: Gemini 3.8 Flash → Grok 4.6). Claude Opus is not used anywhere.
* Each attempt is capped by the remaining request budget; skip a fallback if < 12 s remain.
* Fall through to the next endpoint only on timeout, 429, 5xx, or network error. A 400/401/403 is a configuration problem: stop and return `LLM_ERROR` with the status.
* Reply text may be a string or an array of content blocks: keep only `type: 'text'` parts (as in the original `extractReplyText`).

Renders are serialized in `render.mjs` (`MAX_CONCURRENT_RENDERS = 1`, shared jsdom globals). Queue wait counts against the budget; acceptable for the MVP, revisit if concurrent use grows.

## 5. Error handling

All errors return `isError: true` with JSON `{ status: "ERROR", errorCode, message, stage }`.

| Code | When |
|---|---|
| `INVALID_INPUT` | No input, more than one input, `fileBase64` without `fileName`, oversize file, `/Volumes` path |
| `UNSUPPORTED_FILE` | Original extractor throws `UnsupportedFileError` |
| `ACCESS_DENIED` | `workspacePath` outside caller's home, no forwarded token/email, or export returns 401/403 |
| `EXTRACTION_FAILED` | Export/parse failure or empty text |
| `LLM_TIMEOUT` | Budget exhausted during an LLM step |
| `LLM_ERROR` | All endpoints failed for non-timeout reasons, or a 4xx config error |
| `RENDER_FAILED` | `ValidationError` after the single repair attempt, no time left to repair, or PNG rasterization failed (`pngFailed`; error JSON includes `pngError` and `mermaidSource`) |

PNG rasterization failure (decision Q2): if `renderMermaid` returns `pngFailed: true`, return `RENDER_FAILED` with `stage: "rasterize"`. Exception (D28): if the failure is the renderer's size limit, one resize retry runs first. Do not return the SVG, and do not trigger the LLM repair (the Mermaid source is valid; the fault is the native rasterizer). There is no partial-success response.

## 8a. Tracing and self-observability

Goal: every call and every deployment leaves a machine-readable record that both the user (Catalog Explorer) and the coding agent (Files API / SQL `read_files`) can inspect, without app log access (the agent's `apps logs` access fails in this workspace) and without calling the app URL.

Location: `/Volumes/users/tom_jacobson/lancelot_traces/` (decision D4). Writes use the Files API (`PUT {host}/api/2.0/fs/files/Volumes/...`) with the app service-principal token from `getAccessToken()`. No SQL warehouse.

Layout:

```text
lancelot_traces/
├── latest/startup-report.html   # copy of the most recent startup report, overwritten on each start (D14)
└── runs/<YYYY-MM-DD>/<runId>/
    ├── started.json        # tiny marker written when the run begins (survives a crash mid-run)
    ├── trace.json          # full structured trace, written after the response is sent
    ├── report.html         # startup runs at debug only: single self-contained HTML report (§8b)
    └── artifacts/          # APP_TRACE_LEVEL=debug only
        ├── input.bin           # original file bytes (fileBase64 / workspacePath)
        ├── extracted.txt       # text passed to the LLM
        ├── llm/                # one JSON file per LLM attempt, including failed and fallback attempts
        │   └── <step>-<n>-<endpoint>.json   # step = ping | select | generate | repair; request messages,
        │                                    # max_tokens, HTTP status, ms, usage, full reply body OR full error body
        ├── attempt1.mmd, attempt2.mmd   # every Mermaid attempt (attempt2 only if a repair ran)
        └── output.png          # final PNG (no SVG is saved, decision D10)
```

`runId` format: `<kind>-<UTC timestamp>-<random>`, where kind is `call` or `startup`. The runId is returned to the caller in the response JSON (success and error) so a specific call can be looked up.

`trace.json` contents (all levels unless noted):

| Section | Fields |
|---|---|
| run | runId, kind, startedAt, finishedAt, totalMs, budgetMs (70000), outcome (`OK` or error code), errorStage |
| version | git commit and timestamp from `VERSION.json`, Node version, package versions of mermaid/jsdom/resvg/pdf-parse, `DATABRICKS_APP_NAME` |
| config | trace level, primary/fallback endpoint names, resolved volume path |
| caller | input fields present, `x-forwarded-email` if present (hashed at `production`), whether a forwarded token was present (never the token) |
| input | mode, fileName, extension, encoded and decoded bytes, SHA-256, workspacePath, validation result and error reason |
| extract | extractor branch, ms, character count, truncated flag; preview of first 500 chars (debug only) |
| select | skipped (diagramType given) or: attempts[], parse outcome (`parsed`, `defaulted_to_flowchart`), chosen type, rationale (debug only) |
| generate / repair | attempts[]: endpoint, ms, HTTP status, fallback reason, prompt and completion token usage; fenced block found (yes/no); Mermaid length and SHA-256 |
| llm (all steps) | Every attempt is recorded, not only the one that succeeded: failed attempts (timeout, 429, 5xx, 4xx, network error, empty reply) and fallback attempts keep their HTTP status, error class, and (debug only) the full error body in `artifacts/llm/`. Startup endpoint pings use the same record format |
| render | attempts[]: ms, outcome (`ok`, `validation_error`, `png_failed`, `timeout`), error message (redacted at `production`), PNG bytes, width and height (read from the PNG header), PNG SHA-256 |
| response | status sent, content types, response bytes, whether the HTTP response finished or the connection closed first |
| tracer | any trace-write failures from earlier writes in this run |

Trace levels (`APP_TRACE_LEVEL`, decision D6):
* `debug` (build and test): everything above plus the `artifacts/` folder.
* `production`: metadata only. No `artifacts/`, no previews, no rationale. Error messages from the renderer and LLM endpoints are reduced to error class and a fixed-length, non-content summary, because they can contain fragments of the document or Mermaid source. Caller email is hashed.

Write strategy:
* `started.json` is written when the run starts (one small PUT, awaited with a short timeout, never blocks past 2 s).
* `trace.json` and artifacts are written after the MCP response has been sent, so tracing does not consume the 70 s budget.
* Every write has its own `.catch()`; a trace failure is logged to stdout and recorded in the next write, but never changes the tool result and can never raise an unhandled rejection (guide lesson 5.3).
* Fault injection for the manual V19 test only (D17): `TRACE_FAULT_INJECT` (path substrings whose writes fail on purpose, before any network call) plus a required `TRACE_FAULT_INJECT_UNTIL` (ISO timestamp, future, at most 2 h after process start; injection switches itself off when it passes). Missing or invalid `UNTIL` means injection stays off and the reason is recorded. Never set in `app.yaml`; supplied only as a one-off deployment override. Injected failures are marked `"injected": true` in `tracer.writeErrors`, and the state is shown in `/health` and the report summary.

Startup self-test (`STARTUP_SELFTEST`, runs once per process start, after `listen()`, in the background):
* `render`: renders a two-node flowchart, plus a gallery of all 32 `DIAGRAM_CATALOG` entries from `diagramTypeTestSnippets.mjs` (D13): the 28 supported types and the 4 known-unsupported ones (Architecture, Mindmap, Agentflow, Use case), which are labeled "known unsupported" and re-checked each run. Records pass/fail, ms, PNG bytes, and error message per type. At `debug`, each gallery PNG is saved as `artifacts/gallery/<type>.png`. Gallery failures are expected for some types (several render only in a real browser) and never fail the self-test; they are reported, not blocking.
* `full` (default during development): `render`, plus a minimal ping to each LLM endpoint (traced like any other LLM attempt, §8a llm row), a Files API write/read check on the volume, plus extraction-only checks of `selftest/sample.docx`, `sample.xlsx`, and `sample.json` (extractor branch, character count, truncated flag; no LLM calls), plus one end-to-end pipeline run on `selftest/sample.pdf` through the same code path as a real call. All four are non-sensitive Pokémon content (no real data), so `debug`-level artifacts from the self-test are not affected by Q6.
* `off`: nothing.

## 8b. Startup HTML report

The last step of every startup self-test at `APP_TRACE_LEVEL=debug` writes one self-contained HTML file (`runs/<date>/<runId>/report.html`) and copies it to `latest/startup-report.html` (D14). It is the user's primary review artifact for the Phase 1 gate (D11). Built by `lib/report.mjs` from the in-memory startup trace (D15).

Format:
* One file, no dependencies: inline CSS, PNGs embedded as `data:image/png;base64` URIs, no JavaScript, no external links, so it opens identically anywhere, offline.
* Collapsible sections with native `<details>`/`<summary>`. Large sections (prompts, replies, extracted text) start collapsed.
* All untrusted content (document text, Mermaid source, LLM replies, error messages) is HTML-escaped and shown in `<pre>` blocks, never inserted as markup.
* Not written at `production` (it contains document content).
* Viewing: download from Catalog Explorer and open in a browser (volumes are not expected to render HTML inline).

Sections, in order:
0. Main result (top of the page, always expanded): the final PNG for `sample.pdf` at full width, rendered server-side by `render.mjs` from the Mermaid source the LLM wrote, with the chosen diagram type, the source file name, PNG width x height and bytes, and whether a repair attempt was used. If no PNG was produced, this section shows a large ❌ with the failing stage, error code, and error message instead. This is the primary item for the human verifier (V20, D11, D16).
1. Summary: commit and version, start time, total duration, trace level, and ✅/❌ per self-test stage (PDF end-to-end, each extraction check, each endpoint ping, volume write/read, gallery pass count).
2. Gallery grid: one card per diagram type with ✅/❌ (or ❌ known unsupported), duration, PNG thumbnail (CSS-scaled; click-free), or the error message.
3. PDF end-to-end run: extracted text (collapsed); selection outcome, chosen type, rationale; each LLM attempt (step, endpoint, HTTP status, ms, tokens) with request messages and reply or error body collapsed; each Mermaid attempt (with its render outcome); the final PNG is shown in section 0 and linked from here.
4. Extraction-only checks (DOCX, XLSX, JSON): extractor branch, character count, truncated flag, first 1,000 characters (collapsed).
5. Endpoint pings and volume check: status, latency, error body if any.
6. Trace-write errors, if any.

Size: the PNGs dominate (gallery images are rendered at 2400 px wide). Expect a few MB; acceptable for review.
